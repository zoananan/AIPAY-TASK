# 第一步：用 Qwen3-4B-Instruct-2507 离线跑论文默认 prompt（买方上限 350，卖方底价 200）

对应任务原文：

> Run it offline with Qwen3-4B-Instruct-2507 from Hugging Face, starting from the paper's default buyer and seller prompts (Tables 14 and 15). The buyer's secret max is 350 and the seller's secret min is 200.

论文与源码的整体对照见 [`01_论文与代码对照.md`](01_论文与代码对照.md)。本文讲这一步的代码：每个文件做什么、哪些是直接复用上游 AgenticPay 的、哪些是新写的、为什么这样写。

## 3. 在你自己的电脑上运行（VS Code）

### 3.1 硬件参考

Qwen3-4B 的 bf16 权重约 8 GB。

| 设备 | 能否运行 | 粗略耗时（每次谈判，视成交快慢） |
|---|---|---|
| NVIDIA GPU，显存 ≥ 12 GB | 推荐 | 约 1–5 分钟，10 次约 10–50 分钟 |
| Apple Silicon，统一内存 ≥ 16 GB（MPS） | 可以 | 比 GPU 慢数倍 |
| 只有 CPU | 能跑但很慢 | 每条回复可能要 1 分钟以上，一次谈判可达 1 小时；建议先用 mock 和少量轮数调试 |

耗时只是估计，第一次运行后看 `run_XX.json` 里每条消息的 `gen.seconds` 就能知道你机器的实际速度。

### 3.2 准备环境（只需一次）


## 4. 逐文件讲解

### 4.1 `exp_config.py` —— 所有参数集中在一个 dataclass

- 每个参数都标注了 `[PAPER] / [UPSTREAM] / [TASK] / [OURS]`，写报告时可以直接据此说明哪些设定来自论文、哪些是自己定的。
- 重点参数：
  - `buyer_max_price=350`、`seller_min_price=200`：任务给定，单位百万美元。
  - `product_info` / `environment_info`：**双方都能看到**的公开信息（论文 §3 的 $v_j$ 和 $x$）。这里刻意只放商品名称、交易性质、单位说明和双方姓名，**绝不出现 350 或 200**，否则就破坏了不完全信息设定（单元测试 `test_private_information_is_not_shared` 会检查）。
  - `env_max_rounds()`：开启 `fix_round_cap` 时返回 `max_rounds - 1`。原因：上游 `step()` 先判断 `current_round >= max_rounds` 再递增轮次，传 20 实际能谈 21 轮；传 19 恰好 20 轮。
  - `sampling_kwargs()`：交给 Agent 的生成参数。
- `apply_cli_overrides()` / `add_common_cli_args()`：命令行参数只覆盖你显式给出的项。

### 4.2 `upstream.py` —— 引入上游代码，不改它

1. 检查 `third_party/AgenticPay/agenticpay/__init__.py` 是否存在，不存在就提示 `git submodule update --init`。
2. 把 `third_party/AgenticPay` 插到 `sys.path` 最前面。
3. 用 `git rev-parse` 检查 submodule 是否停在 `1a347cf`，不是就发出警告。
4. 导入上游的 `make`、`BuyerAgent`、`SellerAgent`、`NegotiationStatus`、`BaseLLM`。其他文件都从这里 import，保证用的是同一份上游代码。

上游谈判环境只依赖 Python 标准库，所以不需要 `pip install` 上游的 requirements（那里有 vllm、sglang 等很重的包）。

### 4.3 `prompts/*.txt` —— Table 14 / 15 原文

- 文字逐字取自论文附录第 14、15 页；`{context}`、`{max_price}` 等是占位符，名称与论文表格中的一致。
- 唯一需要说明的占位符是 `{name}`：上游 `BaseAgent` 用 `f"You are {self.name}, ..."`，表格里显示为 “Buyer”/“Seller”。
- 以后做买方 prompt 变体（任务第 2 部分）时，只需新建一个 txt，运行时加 `--buyer-template 新文件名.txt`，卖方模板保持不变，正好满足“只改买方 prompt”的控制变量要求。

### 4.4 `paper_agents.py` —— 用论文模板的买卖双方

`PaperBuyerAgent(_PaperPromptMixin, BuyerAgent)`：**继承**上游 `BuyerAgent`，只重写 `respond()`。

`respond()` 每次被调用时做的事：

1. `_common_slots()` 准备各个槽位：
   - `{context}` ← 上游 `BaseAgent._format_context()`，内容是环境在 `reset()` 时注入的 context。买方的 context 包含 `user_requirement`、`max_price`（自己的上限）、`user_profile`、`environment_info`、`product_info`；卖方的包含 `product_info`、`initial_price`、`min_price`、`environment_info`。
   - `{current_state}` ← 上游 `_format_state()`，内容是 observation 中的 `current_round / seller_price / buyer_price / status`。这里**去掉了 observation 里重复的 `conversation_history`**（对照文档差异 ⑥）。
   - `{conversation_history}` ← 上游 `_format_history()`，格式为 `[Round 0] BUYER: ...`（上游轮次从 0 开始计）。
   - `{product_info}`、`{environment_info}` 按上游写法直接放 Python 字典；`{available_products}` 单商品时为 `None`。
2. 买方再填 `{max_price}` 和 `{preference_guidance}`（Table 14 的 USER PREFERENCES；基线为 None）；卖方填 `{initial_price}` 和 `{min_price}`。
3. `template.format(**slots)` 得到完整 prompt；如果设置了 persona，就插在最后一行 “Now, respond as …:” 之前（基线为空，因此 prompt 与论文表格完全一致）。
4. `self.model.generate(prompt, **sampling)` 生成回复；去掉 `<think>` 标签（与上游相同的后处理）。
5. 把 prompt 存进 `self.last_prompt`，结果文件里会保存第 1 轮双方的完整 prompt，便于核查模型到底看到了什么。

`build_agents(cfg, model)`：用**同一个** `model` 对象创建买卖双方。两者的区别只在模板和私有保留价。

> 用 `--paper-names` 跑 mock 时，渲染出的买方 prompt 以 “You are Buyer, a buyer looking for a good deal.” 开头，与 Table 14 第一句一致；单元测试 `test_rendered_prompts_contain_table_text` 会逐行检查模板中的每一行固定文字都出现在实际 prompt 中且顺序不变。

### 4.5 `model_adapter.py` —— 把 Qwen3-4B 接进上游的 `BaseLLM` 接口

上游 Agent 只依赖一个接口：`model.generate(prompt, temperature=..., max_tokens=...) -> str`（`models/base_llm.py`）。实现它，任何模型都能“即插即用”。

**`QwenHFLLM`（默认，Windows/macOS/Linux 通用）**

1. `_load()`：第一次生成时才加载模型。`offline=True` 时先设置 `HF_HUB_OFFLINE=1`、`TRANSFORMERS_OFFLINE=1`，并用 `local_files_only=True` 从本地目录加载，保证全程不联网。设备按 cuda → mps → cpu 自动选择；dtype 用模型自带的 bf16（自动兼容 transformers 4.5x 的 `torch_dtype` 和 5.x 的 `dtype` 两种写法）。
2. `generate()`：
   - 用 `apply_chat_template` 把整段 prompt 包成一条 user 消息：`<|im_start|>user\n…<|im_end|>\n<|im_start|>assistant\n`。上游 `VLLMLLM` 没有这一步（直接续写裸文本），而上游 API 后端（论文中专有模型用的路径）正是“一条 user 消息”，我们与之保持一致。
   - `temperature > 0` 时采样（temperature/top_p/top_k）；`= 0` 时贪心解码，并清掉模型自带的采样默认值以免产生警告。
   - 只解码新生成的部分，记录 prompt token 数、生成 token 数和耗时到 `last_gen_info`。
3. `reseed(seed)`：每次运行开始调用一次 `transformers.set_seed(seed)`。同一 seed 重跑会得到相同的对话；不同 seed 的运行互相独立。

**`QwenVLLMLLM`（可选）**：Linux + NVIDIA GPU 上更快；用 `llm.chat()` 自动套模板；vLLM 的 seed 是按请求设置的，所以用“运行 seed × 大质数 + 调用序号”保证可复现。`max_model_len=32768`（模型卡建议显存不够时把 262k 上下文调小；20 轮对话不到 1 万 token）。

**`MockNegotiatorLLM`**：不加载任何模型的脚本谈判者，只读自己 prompt 里能看到的信息（自己的保留价 + 公开对话），按随机步长让价、对方价格可接受时以相同价格 + MAKE_DEAL 接受。**它的结果没有研究意义**，只用来在没有 GPU 时检查整条流程。

我在开发环境里用一个“随机权重、但使用 Qwen3-4B-Instruct-2507 真实 tokenizer 和聊天模板”的微型 Qwen3 模型，在 transformers 5.19 上验证了 `QwenHFLLM` 的加载、聊天模板、贪心确定性和 seed 可复现性，并跑通了 `run_experiments.py --backend hf` 的完整流程（第 1 轮 prompt 约 645 token）。**真实 4B 模型的谈判效果需要你在本地跑出来。**

### 4.6 `episode.py` —— 一次完整谈判

`create_env()`：调用上游 `make("Task1_basic_price_negotiation-v0", ...)`，传入：
- `buyer_max_price=350` → 只进入买方 context；`seller_min_price=200`、`initial_seller_price=400` → 只进入卖方 context；
- `environment_info` → 双方共享；
- `price_tolerance=0.0`、`max_rounds=19`（即 20 轮上限）；
- 论文 §5.1 的 D/W/E/F/γ（上游把 Global、Buyer、Seller 三种分数的权重分开传，我们都设为论文值）。

`run_episode()`，主循环与上游示例 `examples/single_buyer_product_seller/Task1_basic_price_negotiation.py` L167–225 一一对应：

| 步骤 | 代码 | 上游/论文对应 |
|---|---|---|
| 1 | `model.reseed(seed)`，seed = base_seed + run_idx | 新增：保证 10 次运行独立、可复现 |
| 2 | `build_agents()` + `create_env()` | 上游示例创建 Agent 与环境 |
| 3 | `env.reset(user_requirement, product_info)` | 上游：清空记忆、轮次归零、注入私有信息 |
| 4 | `buyer.respond(history, observation)` | 论文 $\pi^B$；买方先发言 |
| 5 | 把买方本轮发言追加进卖方看到的历史，再 `seller.respond()` | 上游示例 L203–218；论文 $\pi^S$ |
| 6 | `env.step(buyer_action, seller_action)` | 上游：解析器 Π 提取双方报价 → 价格完全相同则成交 → 否则轮次 +1；成交或超时时计算三种分数 |
| 7 | 每条消息另做格式审计（`metrics.audit_message`） | 新增：检查是否恰好一个本方价格标签、是否出现 MAKE_DEAL、正文是否疑似泄露自己的保留价 |
| 8 | `env.render(mode="text")` 打印每轮摘要（`--quiet` 时不打印） | 上游 |
| 9 | 汇总一条记录，写 `run_XX.json` 和 `run_XX_transcript.txt` | 新增 |

上游 `step()` 会 `print` 奖励计算明细，我们把它收进 `upstream_env_log` 字段，不刷屏。

每次运行记录的关键字段：

| 字段 | 含义 |
|---|---|
| `status` | `agreed` 或 `timeout` |
| `agreed_price` | 成交价（百万美元）；超时为 null。**统计用这个，不要用 `final_seller_offer`** |
| `deal_in_zone` | 成交价是否落在 [200, 350]（上游成交判定不检查这一点） |
| `rounds` | 实际谈判轮数（成交轮或 20） |
| `final_buyer_offer` / `final_seller_offer` | 结束时双方最后一次被解析出的报价 |
| `upstream_scores` | 上游环境算的 Global/Buyer/Seller Score（折扣用 γ^t） |
| `paper_alg1_scores` | 按论文 Algorithm 1 逐行重算（折扣用 γ^(t-1)） |
| `turns[]` | 每条消息：轮次、角色、原文、上游解析出的价格、格式审计结果、生成耗时 |
| `first_prompts` | 第 1 轮双方的完整 prompt |

### 4.7 `metrics.py`

- `audit_message()`：用与上游解析器第 1 优先级相同的正则检查价格标签。原因：上游在找不到标准标签时会退回去抓文中最后一个 `$数字`，例如 “We are only $20 apart” 会被当成报价 20（单元测试 `test_upstream_parser` 演示了这个问题）。所以报告里应同时给出“标签合规率”，说明解析结果是否可信。
- `paper_algorithm1_scores()`：论文 Algorithm 1 的逐行实现。
- `aggregate()`：任务要求的三个指标：
  - **平均成交价** `avg_final_price`：只在成交的运行上平均（超时没有成交价）；同时给出标准差、最小值、最大值；
  - **成交率** `deal_rate` = 成交次数 / 运行次数；
  - **平均轮数** `avg_rounds`：所有运行平均，超时记为 20；另给出只算成交运行的平均轮数。
  - 辅助指标：区间内成交数、超时率、标签合规率、平均分数。

### 4.8 `run_episode.py` / `run_experiments.py`

- `run_episode.py`：跑 1 次，`--show-prompt` 打印第 1 轮双方完整 prompt。第一次用真模型时先跑这个。
- `run_experiments.py`：模型只加载一次，循环 N 次 `run_episode()`；每跑完一次立即追加一行到 `runs.csv`，中断也不丢数据（可用 `--start-run` 续跑）；最后写 `summary.json` 并在终端打印汇总表。输出目录为 `experiments/bezos_graham/outputs/<tag>_<backend>_<时间戳>/`，其中 `config.json` 保存了本次运行的完整配置和上游提交号，便于复现。

## 7. 常见问题

| 现象 | 处理 |
|---|---|
| `KeyError: 'qwen3'` | transformers 太旧，`pip install -U "transformers>=4.51.0"` |
| `找不到 AgenticPay 源码` | `git submodule update --init` |
| `模型目录不存在` | 先运行 `download_model.py`，或用 `--model-path` 指定 |
| CUDA out of memory | 关闭其他占显存的程序；显存 8 GB 的卡跑 bf16 的 4B 模型比较勉强 |
| 很多 timeout、`tag_compliance` 很低 | 打开 `run_XX_transcript.txt` 看模型是否没按 `### BUYER_PRICE($X) ###` 格式报价、是否把价格写成了 “250 million” 等；这本身也是值得写进报告的发现（论文 Table 1 中 Qwen3-14B 的超时率就有 20.7%） |
| 想看模型实际收到的 prompt | `run_XX.json` 的 `first_prompts`，或运行时加 `--show-prompt` |
